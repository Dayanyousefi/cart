# معماری فنی پلتفرم دعوتنامه دیجیتال (ARCHITECTURE.md)

## ۱. بررسی محیط اجرایی (Google AI Studio vs. Production Ubuntu VPS)

پیش از انتخاب معماری، محدودیتها و امکانات واقعی محیط فعلی بررسی شد:

### الف) ویژگیها و محدودیتهای محیط Google AI Studio
1. **تکپورت بودن پیشنمایش (`PORT=3000`):** تمام درخواستهای فرانتاند و بکاند (`/api/*`) و صفحات عمومی (`/i/:slug`) باید از طریق یک سرور واحد روی پورت `3000` پاسخدهی شوند.
2. **عدم وجود демон Docker و Redis محلی در کانتینر پیشنمایش:** در محیط AI Studio نمیتوان سرویسهای Docker Compose یا Redis/Nginx را بهصورت فرآیند پسزمینه سیستمfaktor اجرا کرد، اما میتوان کدهای کامل `Dockerfile`، `docker-compose.yml` و `nginx.conf` را برای استقرار روی VPS تولید و نگهداری نمود.
3. **دیتابیس در محیط توسعه و Production:** PostgreSQL بهعنوان دیتابیس اصلی انتخاب شده است. برای اجرای بدون وقفه در محیطهایی که هنوز PostgreSQL متصل نشده، لایه Repository از الگوی Adapter پشتیبانی میکند تا تمام تراکنشها، قیدهای یکتایی (Unique Constraints) و روابط کلید خارجی بهصورت دقیق اجرا شوند.
4. **پرهیز از تحمیل Next.js:** از آنجا که استارتر پروژه بر پایه **React 19 + Vite 8 + Express 4 + TypeScript** است، مهاجرت اجباری به Next.js باعث شکستن ساختار استاندارد بیلد محیط میشود. بنابراین از معماری **Full-Stack Express + Vite SPA/SSR-Meta Middleware** استفاده میکنیم.

## ۲. الگوی معماری: Modular Monolith

سیستم بهصورت یک **Modular Monolith لایهبندیشده** طراحی شده است. هیچ ماژولی اجازه ندارد مستقیماً به جداول دیتابیس ماژول دیگر 쿼ری بزند، بلکه ارتباط بین ماژولها از طریق Service Interface مشخص انجام میشود.

+-----------------------------------+-----------------------------------+
                                    | HTTPS / REST JSON API (/api/v1/*)
                                    v
+-----------------------------------------------------------------------+

## ۳. لایهبندی داخلی هر ماژول سمت سرور

هر ماژول در مسیر `src/server/modules/<module-name>/` دارای ۴ لایه مجزا است:

1. **`<module>.validation.ts`:** اسکیماهای اعتبارسنجی ورودی (Body, Query, Params) در سمت سرور. هیچ دادهای بدون عبور از این لایه وارد Controller نمیشود.
2. **`<module>.controller.ts`:** دریافت درخواست HTTP، استخراج کاربر احراز هویت شده، فراخوانی Service و بازگرداندن پاسخ استاندارد HTTP.
3. **`<module>.service.ts`:** منطق تجاری (Business Logic)، بررسی مالکیت منابع (Ownership Check برای جلوگیری از IDOR)، محاسبه قیمت سمت سرور و مدیریت تراکنشها.
4. **`<module>.repository.ts`:** تنها لایه مجاز برای تعامل با دیتابیس و اجرای کوئریهای بهینه.

## ۴. معماری موتور قالبها (Template Engine) و جداسازی داده از نمایش

یکی از مهمترین نیازمندیهای محصول این است که **ویرایش یک قالب توسط ادمین نباید دعوتنامههای قبلی کاربران را ناخواسته تغییر دهد** و **هیچ کد جاوااسکریپت دلخواهی نباید توسط کاربر یا قالب اجرا شود**.

### الف) ساختار Declarative JSON Schema برای قالبها
هر نسخه از قالب (`template_versions`) شامل یک تعریف JSON ساختاریافته و امن است:
- **`layout`:** چیدمان بخشها (`hero`, `hosts`, `story`, `schedule`, `venue_map`, `gallery`, `rsvp_form`, `countdown`).
- **`typography`:** فونتهای مجاز فارسی (`Vazirmatn`, `Lalezar`, `Sahel`, `Parastoo`) و مقیاس اندازهها.
- **`palette`:** رنگهای پسزمینه، متن، حاشیههای طلایی/کلاسیک و دکمهها.
- **`editableFields`:** فهرست فیلدهایی که کاربر مجاز به تغییر آنهاست همراه با محدودیت طول کاراکتر و نوع داده.
- **`animations`:** شناسه انیمیشنهای ازپیشخصیصیافته و امن CSS/Motion (`fade-up`, `floral-reveal`, `envelope-open`) — بدون هیچگونه `eval` یا `dangerouslySetInnerHTML`.

### ب) مکانیزم Versioning و Snapshot در لحظه ساخت/انتشار
1. وقتی ادمین قالب را تغییر میدهد، یک رکورد جدید در جدول `template_versions` با شماره نسخه بالاتر (`version_number + 1`) ساخته میشود.
2. هر دعوتنامه در جدول `invitations` به یک `template_version_id` مشخص متصل است و علاوه بر آن، در زمان انتشار (`PUBLISHED`) یک کپی تغییرناپذیر (`template_snapshot_json`) از ساختار ظاهری همان نسخه قالب ذخیره میکند.
3. بنابراین حتی اگر قالب اصلی غیرفعال شود یا نسخه جدیدی بگیرد، دعوتنامههای منتشرشده قبلی دقیقاً با همان ظاهر تضمینشده نمایش داده میشوند.

## ۵. معماری لینک اختصاصی (`/i/:slug`) و سئو (SEO / OpenGraph)

- آدرس عمومی دعوتنامهها بر پایه مسیر (`Path-Based URL`) در قالب `https://example.ir/i/:slug` (مثلاً `https://example.ir/i/dayan123`) تولید میشود.
- زمانی که خزندههای شبکههای اجتماعی (تلگرام، واتساپ، ایتا، بله) یا مرورگر مهمان آدرس `/i/:slug` را درخواست میکنند، سرور Express قبل از ارسال HTML، متادیتای اختصاصی آن مراسم (`<title>`، `og:title`، `og:description`، `og:image`) را بهصورت داینامیک در فایل HTML تزریق میکند تا پیشنمایش لینک در پیامرسانها کاملاً حرفهای نمایش داده شود.
- صفحه عمومی فاقد هرگونه بارگیری کدهای سنگین داشبورد یا پنل مدیریت است تا در اینترنت موبایل با سرعت پایین در کمتر از ۱.۵ ثانیه بارگذاری شود.

## ۶. معماری پرداخت امن (Adapter Pattern)

فرآیند پرداخت بر پایه اصول زیر طراحی شده است:
1. **عدم اعتماد به کلاینت:** قیمت پایه (`50,000` تومان یا قیمت اختصاصی قالب) و تخفیف کوپن صرفاً در سمت سرور و از روی دیتابیس محاسبه میشوند.
2. **الگوی Adapter (`PaymentGatewayAdapter`):** رابط استاندارد شامل متدهای `requestPayment()` و `verifyPayment()` است.
3. **جلوگیری از تایید کاذب و Double Spending:**
   - بازگشت کاربر به صفحه Callback بهمنزله موفقیت پرداخت نیست.
   - سرور با استفاده از `authority` / `trackId` و مبلغ دقیق سفارش، متد `verifyPayment` درگاه را از سمت سرور فراخوانی میکند.
   - تمام مراحل در یک تراکنش دیتابیس (`BEGIN ... COMMIT`) با قفل ردیف سفارش (`SELECT ... FOR UPDATE`) انجام میشود تا ارسال همزمان دو Callback تکراری نتواند سفارش را دوبار پردازش کند.
   - تمام رویدادهای درگاه در جدول `payment_events` ثبت میشوند.
